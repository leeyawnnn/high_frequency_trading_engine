# Reports and figures

Everything here is generated. Nothing is hand-maintained, and the numbers in
the top-level README come from these files rather than being transcribed into
it.

## Regenerating

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
scripts/measure.sh                  # latency run, microbenchmarks, tables
python3 tools/load_sweep.py         # latency vs offered load
python3 reports/plot.py             # figures (needs matplotlib)
```

`scripts/measure.sh` writes a `.meta.json` beside every artifact recording the
exact command, the commit, the UTC timestamp, the CPU, the core count, the OS,
and the load average when the run started. A latency number without its
machine is not a result, and one taken on a busy machine is a different result
again.

The latency run passes `--wait spin` deliberately. That is the low-latency
policy and it assumes a free core per stage; it is not the engine's default.
See "Measurement methodology and its limits" in the top-level README.

## What is here

| file | contents |
|---|---|
| `data/summary.csv` | per-stage percentiles, with clock resolution and source |
| `data/{feed,strategy,gateway,e2e,round_trip}.csv` | raw histogram buckets |
| `data/components.csv` | hot-path microbenchmarks, median and IQR |
| `data/false_sharing.csv` | padded vs unpadded SPSC queue |
| `data/load_sweep.csv` | latency as a function of offered rate |
| `data/latency_run.txt` | the run log, including the clock self-check |
| `tables.md` | the tables, rendered from the CSVs. Do not edit by hand. |
| `figures/*.svg` | the figures, rendered from the CSVs |

`tables.md` is regenerated by `tools/render_tables.py` and CI fails if it
drifts from the CSVs. That check exists because the previous version of this
repository published a strategy p50 of "~0 ns" beside a `summary.csv` that
said 399 ns, in the same commit.

## Figures

**`fig_latency_vs_load.svg`** — end-to-end latency against offered message
rate. Read the knee: the engine tracks the sender to 400k msg/s and saturates
near 590k, and the p99 grows roughly 60x across the range while the median
grows under 2x. This is the most useful chart here, because "how fast is it"
matters less than "where does it stop coping".

**`fig_e2e_ccdf.svg`** — the complementary CDF of end-to-end latency, on log
axes. Plotted as 1−F rather than F so the tail is legible; a plain CDF puts
everything past p99 in the top pixel row, which is the part worth seeing.

**`fig_stage_percentiles.svg`** — per-stage percentiles against the whole
path, with the clock's two-tick resolution floor drawn as a shaded band. Bars
labelled `<2` are sitting on that floor and are upper bounds, not
measurements. The point of the figure is the gap: the three stages together
account for a small fraction of end-to-end, and the rest is queue wait and
scheduling.

**`fig_components.svg`** — isolated hot-path costs, sorted, with the
inter-quartile range as error bars and the empty-loop barrier baseline as a
reference line. `tsc_now` sits on that line, which is the honest way of saying
its cost is not separable from the harness measuring it.

**`fig_false_sharing.svg`** — the padded vs unpadded SPSC queue.

## Measured here

Apple M4, 10 logical cores, macOS 26.6.1, threads unpinned (macOS exposes no
`pthread_setaffinity_np`), spin wait policy, 4 seconds at 100k msg/s. Market
data is synthetic, produced by the bundled `SimExchange` over loopback UDP.

See `tables.md` for the current figures rather than a copy of them here.

## Things worth knowing about this data

**The tail is scheduling, not code.** Per-stage processing is tens to hundreds
of nanoseconds; end-to-end p99 is tens of microseconds. The difference is
queue wait and OS preemption on unpinned threads. A sub-microsecond p99 is a
pinned-Linux target with `isolcpus` and `nohz_full`, and this repository has
not demonstrated one. It is listed as not done rather than claimed.

**Cache-line padding measures backwards on this hardware.** The unpadded queue
runs about 4x faster than the padded one on this M4 (112.7 vs 26.9 M ops/s).
The plausible mechanism is that Apple Silicon's cores sit in clusters with a
128-byte line, so keeping both cursors on one line moves one line between
clusters per hand-off instead of two. It is measured with the two queues
identical apart from the `alignas` — an earlier version also omitted the
cached-cursor optimisation from the unpadded side, which made the comparison
report the opposite answer for the wrong reason. It has not been measured on
x86, where the textbook result is likely to hold, so the padding stays.

**Loopback `sendto` has a syscall ceiling** of roughly 0.3 M datagrams/s, which
is why the feed handler batches multiple messages per datagram to sustain over
1 M msg/s. It is also, in miniature, the reason production systems use kernel
bypass.

## Bugs found by measuring rather than reading

- `mrs cntvct_el0` silently returned garbage: in AArch64 inline assembly `;`
  begins a comment, so `"isb; mrs ...; isb"` dropped the actual read. A
  calibration sanity check caught it; nothing crashed.
- A bus error in the histogram from an unsigned underflow in the HdrHistogram
  index arithmetic in the first octave, turning a small index into roughly four
  billion. ASan made it obvious.
- `::htons` does not compile: it is a function-like macro on both macOS and
  glibc, so it cannot be scope-qualified.
- Zero orders in the two-process run, because the book window's base price
  equalled the exchange's starting mid, so every bid fell below the window and
  was dropped, leaving a one-sided book and no signal. The in-process run had
  masked it by random-walking upward.
- A zero-size Add promoted an empty price level to the top of book, so
  `best_bid_size()` returned 0 while `has_bid()` returned true and
  `imbalance()` produced a signal from a level holding nothing. Found by
  per-message invariant checks, not by the differential test against the
  reference book, which sampled every 1024 messages and missed it.
